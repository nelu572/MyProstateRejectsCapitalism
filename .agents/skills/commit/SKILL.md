# 커밋

## 메시지 규칙

- 제목은 `type: 요약` 형식으로 작성한다. 스코프는 사용하지 않는다.
- 타입은 아래 8개 중 하나를 사용하고, 요약은 한국어로 간결하게 작성한다.
- 본문은 변경 이유나 주의사항을 설명할 필요가 있을 때만 추가한다.

| 타입 | 용도 |
| --- | --- |
| `feat` | 새 게임 기능·콘텐츠 추가 |
| `fix` | 오류·회귀 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 자동 테스트·검증 코드 변경 |
| `docs` | 기획·프로젝트·Notion 문서 변경 |
| `chore` | 빌드·패키지·저장소·도구 설정 변경 |
| `perf` | 기능을 유지하는 성능 개선 |
| `art` | 그래픽·애니메이션·사운드 등 아트 에셋 추가·수정 |

새 게임 동작이나 콘텐츠 구현은 `feat`, 아트 에셋 자체의 작업은 `art`로 분류한다.

예시:

```text
feat: 플레이어 이동 추가
fix: 재시작 후 점수가 유지되는 오류 수정
art: 플레이어 스프라이트 추가
chore: 커밋 스킬 추가
```

## 수행 절차

1. 현재 브랜치, `git status`, 스테이징된 변경과 스테이징되지 않은 변경을 확인한다. 기존 커밋 이력도 참고하되 위 타입과 스코프 없는 형식을 우선한다.
2. 요청 범위에 해당하는 변경만 포함한다. 기존 스테이징에 무관한 변경이 있으면 임의로 포함하거나 해제하지 말고 범위를 확인한다. Unity 에셋의 추가·이동·삭제에는 대응하는 `.meta` 변경도 포함한다.
3. 변경에 맞는 검증을 수행하고, 실행하지 못한 검증은 이유와 함께 명시한다. 문서·스킬만 바뀐 경우 게임 빌드는 요구하지 않는다.
4. 사용자가 커밋을 명시적으로 요청했을 때만 실행한다. 메시지 제안 요청은 메시지 작성으로 마친다.
5. 커밋 직전에 대상 파일, 커밋 메시지, 검증 결과, 현재 브랜치를 간략히 보고한다. 이미 요청된 커밋은 추가 승인 없이 진행한다.
6. 대상 파일을 명시하여 스테이징하고 최종 diff를 확인한 뒤 커밋한다. 완료 후 커밋 해시와 남은 변경을 확인해 알린다.
