# 작업 및 Worktree 관리

**작업 시작 → 구현 → 검증 → 사용자 검토 → 수정(필요 시) → 최종 승인 → 정리**

## 기본 절차

1. **작업 시작:** 요청 범위와 완료 조건을 확인한다. 현재 브랜치, `git status`, `git worktree list`로 기존 작업을 파악한다. 관련 지침과 필요한 기획 부분만 확인한다.
2. **구현:** 현재 요청을 작고 독립적인 단위로 구현한다. 중요한 설계·기획 판단이나 범위 변경이 필요할 때만 먼저 승인받는다.
3. **검증:** 변경에 맞는 최소한의 검증을 수행한다. 코드·Editor 변경은 Unity MCP로 컴파일 오류와 관련 동작을 확인하고, 에셋은 실제 Unity 환경에서 확인한다. 빌드 관련 작업은 [릴리스 지침](RELEASE.md)을 따른다. 문서만 바뀌면 링크와 Git diff를 확인하며 게임 빌드를 요구하지 않는다. 실행하지 못한 검증은 이유를 보고한다.
4. **사용자 검토·수정:** 구현 결과와 검증 결과를 보고하고 피드백을 반영한다. 구현 완료를 최종 승인으로 간주하지 않는다. 승인 전에는 원본·후보·복구 가능한 작업 환경을 유지한다.
5. **최종 승인·정리:** 사용자의 명시적인 최종 승인 후 관련 임시 산출물을 정리한다. 아래 삭제 안전 규칙을 따른다.

새 변경, 검증 실패, 미해결 문제가 없다면 통과한 검증을 불필요하게 반복하지 않는다.

## Unity Editor 유지 및 MCP 장애 대응

- 모든 작업에 [Editor 종료 금지 및 비파괴적 연결 복구 지침](../AGENTS.md#editor-종료-금지-및-비파괴적-연결-복구--이후-모든-작업에-적용)을 적용한다. 사용자 승인 없는 Editor 종료·재시작과 이를 유발하는 메뉴·API·자동화·강제 종료를 실행하지 않는다.
- MCP 장애는 기존 Editor 프로세스를 유지한 상태에서 복구한다. 복구가 어려우면 해당 검증을 보류하고 문제와 미검증 항목을 보고한다.
- 기존 임시 종료 차단을 유지한다. 원인 조사나 재현을 위해 종료 명령을 시험하지 않는다.
- 반드시 필요한 Editor 재시작도 이유와 영향을 설명한 후 해당 작업에 대한 별도 사전 승인을 받아야 한다.

## Worktree 정책

- 독립적인 병렬 작업에만 Worktree를 사용한다. 간단한 변경이나 순차 작업에는 새 Worktree를 만들지 않는다. Worktree 사용 자체가 병렬 작업 지시는 아니다.
- 생성 시 담당 범위, Worktree 경로, 작업 브랜치와 기준 브랜치·시작 커밋을 작업 보고에 명확히 남긴다. 새 브랜치의 기본 접두사는 `feature/`다.
- 다른 Worktree의 파일을 직접 수정하지 않는다. 변경이 필요하면 해당 작업과 조율한다.
- 작업이 완료됐어도 최종 승인 전에는 관련 결과물, 브랜치와 Worktree를 보존한다.
- 병합·Push는 사용자가 요청하거나 명시적으로 승인한 경우에만 수행한다.
- 커밋은 명시적으로 요청된 경우에만 [기존 커밋 스킬](../.agents/skills/commit/SKILL.md)을 사용한다. 승인 전 보존을 이유로 자동 커밋하지 않는다.

## 승인 후 정리와 삭제 안전

- 해당 작업에서 만든 불필요한 임시 파일, 생성된 검증 결과물과 중복 산출물만 정리한다. 출처나 필요 여부가 불명확하면 보존한다.
- Worktree나 브랜치 제거 전에는 다음을 확인한다.
  - 대상 경로와 브랜치가 현재 작업의 것인지, 커밋 상태와 미커밋·미추적·무시된 파일에 보존할 내용이 없는지.
  - 의도한 대상 브랜치에 병합됐는지, 미병합 작업이 없는지.
  - 필요한 원본과 사용자 보호 대상 파일이 보존됐는지, 복구에 필요한 커밋이나 별도 원본이 실제로 남아 있는지. Git에 없는 파일은 커밋만으로 복구되지 않는다.
- 미병합 작업, 필요한 원본, 사용자 보호 대상 파일을 삭제하지 않는다. 광범위한 일괄 삭제와 강제 제거로 점검을 우회하지 않는다.
- **Worktree·브랜치의 실제 제거처럼 복구가 어려운 조치는 대상과 점검 결과를 제시하고 별도 확인을 받는다.** 일반적인 최종 승인을 제거 승인으로 확대 해석하지 않는다.
- 정리 자체가 새로운 작업보다 커지지 않도록 한다. 불확실한 항목은 남은 문제로 보고한다.

## 완료 보고

아래 네 항목을 간결하게 보고한다.

- 구현 내용: 변경 파일과 핵심 결과.
- 검증 결과: 수행한 확인, 통과 여부와 실행하지 못한 항목.
- 남은 문제: 제한, 미확정 사항 또는 없음.
- 승인 및 정리 상태: 검토 대기 / 수정 중 / 최종 승인, 보존 중인 결과물과 정리 여부.
